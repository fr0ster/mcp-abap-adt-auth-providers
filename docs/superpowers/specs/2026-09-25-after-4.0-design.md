# After 4.0: the deferred findings, closed

**Status:** draft for the owner's approval. The plan follows it as a
separate step.

## Goal

Close everything the 4.0.0 reviews deferred as "not blocking", so the package
carries no known loose ends. One PR, released as **4.1.0**, because refusals
get stricter.

This adds no providers, no features and no public-API changes.

## What changes

### 1. The package declares nothing that does not work

The `bin` field names `auth-authorization-code` and `auth-client-credentials`.
Neither can run from an npm install:

- both point at `.ts` files with a `#!/usr/bin/env tsx` shebang, and `tsx` is
  a devDependency;
- both import `../src/…`, and `src` is not published;
- `auth-authorization-code` imports `@mcp-abap-adt/auth-stores`, which is also
  a devDependency.

They were developer test commands, undocumented in the README, and their
default callback port of 3001 breaks the 61001+ rule.

**Decision (owner, 2026-09-25):** remove them.

- Delete `bin/`, and remove the `bin` field and `bin` from `files`.
- Remove `tsx`, a devDependency that only `bin/` used.
- Keep `@mcp-abap-adt/auth-stores` as a devDependency. Three test suites import
  `AbapServiceKeyStore` from it at the top level:
  `src/__tests__/auth/browserAuth.integration.test.ts`,
  `src/__tests__/providers/ClientCredentialsProvider.test.ts` and
  `src/__tests__/providers/AuthorizationCodeProvider.test.ts`. Replacing it
  with local fixtures is outside this goal. So the dev tree keeps its nested
  `interfaces-auth@1.2.0`, which `auth-stores@1.2.0` brings in, until
  `auth-stores` itself moves to `interfaces-auth@^2`.
- Update the `AGENTS.md` line that describes `bin/`.

This is not a breaking change: the commands never ran from npm.

### 2. Refusal has no side door

- **SAML 1.x.** The rule that every `Assertion`/`EncryptedAssertion` must be
  the signed one, or inside it, covers the SAML 1.x assertion namespace
  (`urn:oasis:names:tc:SAML:1.0:assertion`) as well as SAML 2.0. Today a SAML
  1.x `Assertion` in an unsigned `Extensions` passes the assertion-only
  validator.
- **`idpInitiated` with `authnRequestId`.** A configuration carrying both is
  refused at construction. Today it is refused only after `authorize()`
  returns, which is after the user has been through the browser.
- **An assertion hidden inside a signature.** *(Added 2026-09-26 after the
  final review, owner's decision.)* An enveloped signature leaves its own
  `ds:Signature` subtree out of the digest, so anything placed there, for
  example in `ds:Object`, is unsigned. Today the stray-assertion rule counts an
  `Assertion` or `EncryptedAssertion` inside the signed assertion's own
  `ds:Signature` as "inside the signed assertion", and the assertion-only
  validator accepts it. The payload then travels on whole: to UAA through
  `Saml2BearerProvider`, whose default is that validator. This is true of
  4.0.0 too. From now on any SAML 2.0 `Assertion`/`EncryptedAssertion` or SAML
  1.x `Assertion` with a `ds:Signature` ancestor is refused, under both
  validators, at `signedNode`, with its own message. No identity provider has
  a reason to put an assertion inside a signature. This is a third new
  refusal, and it is listed under "what now fails".
- **Identity-provider text in messages.** Every value from the document that a
  refusal message interpolates goes through `quoteUntrusted`, which quotes it
  and caps its length. That includes the post-signature ones: `Status` code,
  issuer, `Destination`.

### 3. Every refusal names its rule

No two rules under one `check` share a message. The known shared ones:

- `bearerConfirmation`: an unexpected `InResponseTo`, a non-bearer `Method`, a
  `NotBefore` still in the future, and the other sub-rules all produce one
  generic message today;
- `notOnOrAfter`: absent and invalid share a message;
- `signedNode`: the three "does not cover the assertion" paths (placement
  mismatch, the one-assertion guard, the wrapping identity checks) share one.

Each gets a message with a distinguishing fragment. Its test asserts that
fragment, so no test can pass on a neighbour's message.

**Revised during plan review (2026-09-26): the third `signedNode` path is
deleted, not given a message.** Read against the code, the wrapping identity
checks in `assertionInside` can no longer refuse anything through
`validate()`. The count check and the placement check already leave the
signed element as the Response root or its single direct-child Assertion. So
there are two paths, count and placement, and each has its own message.
`assertionInside` and its identity checks go. Testing them directly would
mean exporting them from a module, and the package publishes all of `dist/`,
so that would widen the public API. The wrapping attacks stay covered through
`validate()` by the count and placement rules, and the plan names a mutation
for each attack test.

**An element that must appear exactly once says which way it failed.** The
validator reads several elements that must appear exactly once:

- the Response's direct-child `Assertion`, in both the placement check and the
  one-assertion guard (`check: 'signedNode'`);
- each signature's `Reference`: today the message carries the count but the
  same fragment for zero and for several;
- `Status`, and its `StatusCode`, under the signed-Response validator;
- the assertion's `Issuer`;
- `Conditions`;
- `Subject`;
- each candidate's `SubjectConfirmationData`.

That list is complete. It was made by sweeping every count check in
`src/validation/` and `src/auth/samlBearerAssertion.ts`: every `directChild`,
every `directChildren(...).length`, and every `getElementsByTagNameNS` length
test. What the sweep found that is already distinct or needs no rule:

- zero signatures has its own message;
- `Response/Issuer` refuses more than one and allows none;
- `toBearerAssertion` already separates no Assertion, only an
  EncryptedAssertion, and several;
- the stray-assertion rule refuses any count outside the signed one.

The sweep also found one mislabelled count. An `AudienceRestriction` holding
no `Audience` at all is refused today as `does not name us`. It gets its own
reason (`an AudienceRestriction names no audience`), separate from a
restriction that names others and from an assertion with no restriction.

Today "none" and "more than one" share a refusal. In
`SubjectConfirmationData`'s case the only message is "no
SubjectConfirmationData", which is wrong when there are two. From now on each
of these distinguishes **absent** from **more than one** in its message (for
example `carries no saml:Conditions` and `carries 2 saml:Conditions; exactly
one is allowed`), and has a test and a mutation for each half. An empty
`Issuer` stays a third, separate reason. `NameID` is optional and only
surfaced, never refused: when the `Subject` carries none or more than one,
`nameId` is `undefined`. The README says so.

**`bearerConfirmation` is existential, and its message says why every
candidate failed.** An assertion may carry several `SubjectConfirmation`
elements. It is accepted when at least one passes every sub-rule, which is
what the code does today: it skips a failing candidate and goes on to the
next. That does not change. Refusing on the first failing candidate would
refuse a document whose later candidate is valid.

The refusal message is deterministic:

- **Every candidate is evaluated.** A candidate's reason is the first sub-rule
  it fails, taken in this fixed order, which is the code's order today:
  1. `Method` is not bearer;
  2. `SubjectConfirmationData` absent, or more than one (two distinct
     reasons);
  3. `InResponseTo` present when none is expected, or not the expected one when
     one is (two distinct reasons);
  4. `Recipient` is not the ACS;
  5. `NotOnOrAfter` absent or invalid (two distinct reasons);
  6. `NotBefore` invalid;
  7. `NotOnOrAfter` has passed;
  8. `NotBefore` has not arrived.
- **The message lists each candidate in document order with its reason**, for
  example `no bearer confirmation qualifies: #1 Recipient is not the ACS; #2
  NotOnOrAfter has passed`. With one candidate it carries exactly one reason,
  which is what the per-sub-rule tests assert.
- **Before any candidate is looked at, `Subject` must appear exactly once**
  (absent and more than one are distinct refusals, as above). An assertion
  whose single `Subject` carries no `SubjectConfirmation` at all gets its own
  message.
- **The list is capped.** It names at most the first five candidates and then
  `and N more`, so a message stays bounded. Any value it quotes goes through
  `quoteUntrusted`.

Tests: each sub-rule gets its own single-candidate case, asserting that
sub-rule's fragment. A mixed case with a wrong `Recipient` and an expired
candidate asserts both reasons in document order. A case with an invalid
candidate followed by a valid one is **accepted**, which pins the existential
rule: stopping at the first failure would turn that test red.

### 4. Every rule has a test that goes red without it

These test gaps are closed, with no behaviour change:

- The `signature` rows in the e2e matrix assert the message fragment, not just
  `check`. The rows are unsigned, wrong key and tampered after signing.
- The empty-`idpCertificates` provider test asserts `missingFields`, so the
  provider's own length check is load-bearing, not only the shipped
  validator's guard.
- Several cases get their own test:
  - a minted request ID wins over a declared one;
  - `Saml2PureProvider`'s refresh validates again;
  - `signedNode`'s non-`#` URI branch;
  - its reference-not-found branch, reachable via an `Id`/`id`-attribute
    signature;
  - quoting of the root name and the reference URI.
- `readRequiredId`'s absent case gets a mutation that exercises it directly,
  not only through xmldom returning `null`.
- The duplicate `'response'` iteration of the forged-sibling wrapping case is
  removed, because it repeats the wrong-placement test.
- The context tests' comment about `toHaveBeenCalledWith` is corrected: it
  treats undefined-valued keys as absent.
- The Keycloak suite trusts only `KeyDescriptor use="signing"` certificates
  from the metadata.

### 5. Tests take no longer than they need

The e2e suite (`samlValidation.test.ts`, about 42 s) starts a mock IdP per
test, and each start generates a 2048-bit RSA key. Instead, start one IdP per
`signWhat` in `beforeAll` and switch variants with `idp.setVariant()`. Each
test keeps its own replay store and its own assertion identity, so no state
leaks between tests.

### 6. The contract's documentation matches the behaviour

The JSDoc of `IAssertionReplayStore.recordIfUnseen` in
`@mcp-abap-adt/interfaces-auth` says "its expiry plus any clock skew". The
rule is the last instant a validator would still accept the assertion, and
since 4.0.0 that is later than the session expiry.

The interfaces live in a separate repository, so this is a small PR there,
released as `interfaces-auth@2.0.1`. It is documentation only and does not
block the auth-providers PR.

## Constraints

- Everything pluggable stays a strategy. Nothing writes to `process.stdout`.
  Imports come only from `interfaces-auth`, `interfaces-auth-sap` and
  `interfaces-utils`.
- Every new or changed rule has a test that goes red when the rule is
  deleted. A conjunction gets one mutation per half.
- Every test asserts a message fragment unique to its rule.
- Every behaviour change is documented in the README, CHANGELOG and
  `CLAUDE.md`. Stricter refusals are listed under "what now fails".
- `npm run test:stand` passes before the PR goes to review.

## Out of scope

- Providers, grant types, strategies.
- The public API: exports, config fields and error classes stay as they are.
- Restricting SHA-1. It stays documented as accepted, and a consumer can wrap
  a validator.
