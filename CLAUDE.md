# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`@mcp-abap-adt/auth-providers` — a TypeScript npm package providing every implementation of `IAuthProvider` (from `@mcp-abap-adt/interfaces-auth`) for SAP ABAP ADT: the credential a process delegates to, and the token providers behind it. Any provider from this package can be handed to the process with no check of what it is; each answers all four moments of the contract:

```ts
prepare(): Promise<AuthOutcome>;                          // once per connect
establish(logon: ILogonTarget): Promise<AuthOutcome>;      // every logon
authorize(request: IRequestTarget): Promise<AuthOutcome>;  // every request attempt
rejected(rejection: IAuthRejection): Promise<AuthOutcome>; // the system said no
```

`AuthOutcome` is `{ ok: true }` or `{ ok: false, refusal }`, the refusal an `IAuthProviderError` (`IAuthRefusal = IAuthProviderError`, since interfaces-auth 6.0.0; the package is on 7): a frozen object of `kind` (a closed list), `variant` (`saml-assertion`, `snc`, `configuration`), `facts` (allowlisted values only), `reason`, `hint?` and `diagnostics?`, minted only by `@mcp-abap-adt/auth-errors`. What a token provider throws is auth-errors' `AuthProviderFailure` holding one.

**Non-token credentials** — one way in, nothing to refresh:
- **`BasicAuthProvider`** — a user and a password: a header over HTTP, logon parameters over RFC
- **`CertificateAuthProvider`** — a client certificate presented in the TLS handshake of each logon
- **`SamlAuthProvider`** — a SAML session negotiated elsewhere, handed over as cookies
- **`TokenAuthProvider`** — a token from outside this package: `.fixed(token)` or `.from(refresher)`
- **`SncLogonProvider`** — passwordless RFC logon through an installed SNC product (Secure Login Client); see `docs/passwordless-sso.md`

**Token providers** — `BaseTokenProvider extends AuthProviderBase implements IRefreshableTokenProvider`, so each is both an `IAuthProvider` and the stateful token contract the broker's `getTokens()` / `refreshTokens()` still use, with no wrapper. Every token provider takes a required `renewal: IRenewalStrategy` (`refreshThenLogin()`, `refreshOnly()`, or the consumer's — a missing one is `configuration` `required-fields-missing ['renewal']` at construction) and an optional `persistence: ITokenPersistence` (`refreshStatePersistence(write, { onWriteFailure })`, or the consumer's; absent = nothing persisted):
- **`ClientCredentialsProvider`** — `client_credentials`, no user interaction
- **`AuthorizationCodeProvider`** — UAA authorization code, interactive
- **`OidcBrowserProvider`** — OIDC authorization code with PKCE, interactive
- **`OidcDeviceFlowProvider`**, **`OidcPasswordProvider`**, **`OidcTokenExchangeProvider`**
- **`Saml2BearerProvider`** — SAML assertion exchanged for an OAuth2 token
- **`Saml2PureProvider`** — SAML assertion exchanged for session cookies (its `applyToken` override writes cookies, not a header)
- **`UaaPasscodeProvider`** — UAA/XSUAA one-time passcode from `/passcode` (`cf login --sso`), headless

`docs/btp-setup.md` maps each token provider to what it needs on the SAP side (XSUAA client, trust, user, ABAP mapping) and whether ADT accepts its token; every claim is tagged SAP, Community, Measured, Inference or Pending (a check written but not yet run against the real system). Keep the tags honest when changing it; flip a Pending to Measured, with the date, only after the run.
`docs/passwordless-sso.md` covers passwordless logon: SNC over RFC — `SncLogonProvider`, built and measured against a live system — and the HTTP alternatives (X.509 client certificates, SPNego, IAS), still undecided.

Both SAML providers validate the assertion first, through an `IAssertionValidator` (see "SAML assertion validation").

Every token provider that sends a request to an authorization server — all but `Saml2PureProvider` — takes an optional `clientAuthentication: IClientAuthentication`: how its *client* authenticates every request it sends (first token, refresh, device authorization and poll, token exchange). See "Client authentication".

### Rules every provider follows

1. **No exception crosses the contract.** Each of the four methods catches everything its body throws — its own work, a collaborator, and a target (`header`, `cookies`, `logonParameters`, `tlsMaterial` may throw) — and answers Oops. Every provider extends `AuthProviderBase` (`src/auth/AuthProviderBase.ts`), which owns the four methods: each runs its `on…` body inside auth-errors' `guard`, with the operation per moment validated once at construction and `grant()` read once, inside the boundary; a body's answer is normalised (`classifyOutcome`), so an unminted refusal does not pass. `SncLogonProvider` too: its moments are the four SNC operations, so "the SNC provider failed while … (unknown error)" comes from the boundary. A target's answer goes through `relayOutcome`, never passed on as it is; collaborators' answers are awaited normally (a Promises/A+ thenable works) — except the renewal strategy's `next()`, whose answer must be a decision or a plain native promise of one: a foreign thenable, or a promise with an own `then`/`catch`, is refused (`unknown` `renewal-strategy`) and its `then` never called (`isPlainPromise`) — but no foreign `then` is ever called on a thrown value or a target's answer (`markHandled`, `src/auth/handled.ts`; `contract/rule1.test.ts`, `contract/collaboratorThenables.test.ts`, `matrixCoverage.test.ts`).
2. **A refusal carries no secret — so it never carries an error's message.** Every error is minted by auth-errors' builders (`authError[kind](facts, diagnostics?)`) or by `classify(thrown, operation, grant?)`: its facts come only from the allowlists of interfaces-auth (`CONFIG_FIELDS`, `CONFIG_CASES`, `ASSERTION_RULES` with the `check` each fixes, `OPERATIONS`, `SYSTEM_CODES`, `TLS_FAILURE_CODES`, `OAUTH_ERROR_CODES`, `RFC_KEYS`, …) and branded integers; its words are rendered from `kind` and `facts` only; a value that cannot be allowlisted (an SNC library path, a SAML issuer, two URIs) is a diagnostic admitted by its shape at one of the approved extraction sites (`tools/diagnostic-sites.json`), never a word. A thrown value of no known shape is `unknown` with the operation — "`<operation>` failed (unknown error[, CODE])". No `message`, `cause`, `stack` or body of any error reaches a refusal, and a `name` property is never read.
3. **Nothing to add is Ok.** A provider with nothing for a moment writes to no target and answers Ok.
4. **A target's Oops is the provider's to judge.** A provider with no other way in (SNC, certificate) returns the target's Oops as its own; one that has another (a password is also a header) goes on.
5. **`rejected()` blames the credential only when it was refused.** A `401` or `RFC_LOGON_FAILURE` is the credential (`credential-refused`); a `403`, a redirect, a `5xx`, any other status or RFC key is `system-refused` with its verdict (`readRejection`, `src/auth/rejection.ts`); a rejection with neither is `system-refused` `unknown`. For a token provider this is a reading the renewal strategy receives (`cause.reading`): the shipped strategies stop on `not-credential` with that refusal and no request, and renew on `credential` / `unknown`; a fixed credential answers neutrally. SNC explains a GSS code in the error before any of that.
6. **`rejected()` renews through the renewal strategy the consumer gave; retrying is the consumer's.** The strategy is asked before every step (`refresh` with a required `ifCut`, `login`, `stop`; `sentRefreshToken` required after a refresh that failed once sent, absent elsewhere); the provider takes no step it was not asked for, and a renewal that cannot produce a usable credential throws — what follows is the consumer's. A provider never answers Ok without having changed what it presents: a renewal that yields the same credential is the step outcome `unchanged`, and a stop on it is Oops `renewal-unchanged` ("the renewal returned the credential that was refused"). A stop before any step with nothing else to answer is `renewal-declined`.
7. **No implicit defaults — the consumer composes.** A constructor takes every collaborator explicitly (the interactive strategy, the client-authentication strategy, the device-code presenter, the SAML validator and replay store, the SNC locator and probes, the renewal strategy (required) and the persistence strategy (optional; absent = nothing persisted)); no provider builds one of its own when none is given. Static factories (`inBrowser`, `fromTerminal`, `toConsole`, `fromFiles`, `forSecureLoginClient`) assemble a named, common recipe — the consumer, or the broker, still creates the instance from a constructor or a factory.
8. **A bound token travels with its certificate.** A token provider pins its strategy's TLS material once — `tlsMaterial()` read before its first request or logon, checked, its leaf's `x5t#S256` computed, a copy kept for the provider's lifetime (the logon target gets a copy of it each time); a rotated certificate is a new provider. Its leaf's `notAfter` is checked at pin time and before every token request and logon that presents it — `client-certificate` `expired`, nothing sent, a renewal refused whole. Before presenting a token, `establish()` and `authorize()` read its binding (`readBinding`, `src/auth/tokenBinding.ts`): **bound** (a JWT with `cnf`) is presented only with the pinned certificate of that thumbprint, else Oops `token-binding` `bound-to-unpinned` and nothing written; **unbound** (a JWT without `cnf`) goes as a Bearer; **unknown** (anything else, an opaque token above all) is treated as bound when a certificate is pinned and goes as a Bearer when none is. `establish()` decides on the token held and obtains nothing — none, expired or being renewed is unknown. **A held token bound to another thumbprint than the pinned one** (or with an unreadable `cnf`) is unusable, like an expired one: `getTokens()` / `authorize()` renew it through the renewal strategy (`cause.trigger: 'bound-elsewhere'`) and check the new token — still bound elsewhere is committed, recorded as the step outcome `bound-elsewhere`, and a stop on it is `token-binding` `renewed-bound-elsewhere`: `getTokens()` / `refreshTokens()` throw it, `authorize()` answers it. The renewal's error is remembered (`remembered: { token, error }`) and reaches the strategy as `cause.lastRenewal`; the shipped strategies stop on it at `get-tokens` / `authorize` (the same error, no request) and renew once more at `prepare` and `rejected` — `prepare()` no longer clears it; a superseded refused token gets Ok without a renewal, rule 6; a renewal that throws while such a token is held is remembered the same way with its own error (`renewAttempt()` decides, so getTokens, prepare and rejected alike), e.g. `client-certificate` `expired` stays visible, with no token request and no login. An expired token bound to the pinned one (or unbound) is never remembered: each attempt renews it, as before; `establish()` reads it as unknown. With nothing pinned a bound token is refused in `establish()` / `authorize()`, and `getTokens()` returns it. Only `establish()` / `authorize()` present the certificate; a consumer of `getTokens()` / `refreshTokens()` must present it itself.

## Architecture

### Core design principles

**Interface-only communication.** All interaction with external dependencies happens through contract packages: `@mcp-abap-adt/interfaces-auth` (token providers, `IAuthProvider`, strategies, `IClientAuthentication`, `ICertificateMaterial`, callback server, assertion validator and replay store, the error contract's types and allowlists), `@mcp-abap-adt/interfaces-auth-sap` (XSUAA configuration, `ICertificateMaterialLoader`) and `@mcp-abap-adt/interfaces-utils` (`ILogger`). Depend on the contract package whose contracts are used, nothing wider — never `interfaces-adt`, which carries ADT contracts this package does not use. The package does not know about concrete implementation classes from other packages. A logger is `ILogger`, never a local abstraction. The one runtime dependency of the error contract is `@mcp-abap-adt/auth-errors` (builders, `AuthProviderFailure`, `classify` / `readFailure`, `guard`, `relayOutcome`, `logFields`, `sharedAttempt`, `createParties`): no error, word or refusal is built anywhere else. This file does not track version numbers — they lag behind: see `package.json` for the versions in use, and `CHANGELOG.md` for when and why they changed.

**Everything pluggable is a strategy.** Anything a consumer might reasonably want to do differently is expressed as a strategy behind an interface. The package ships the parts and named factories; the consumer composes. This is why an authorization library does not own a socket, a browser or stdin — a consumer may legitimately own them instead.

**No token the provider holds reaches a log line**, and no key material either. `BaseTokenProvider.formatToken` is the one way a token appears in a log, and it yields only `<redacted, N chars>`, never a character of the secret (`noTokensInLogs.test.ts`, which also covers the client-authentication strategies). **No server text reaches anything:** a token endpoint's body is read only for a registered OAuth `error` (`registeredOAuthError`, `oauthErrorBody.ts`: RFC 6749/8628/6750/8693 and OIDC Core §3.1.2.6); its `error_description` and `error_uri` are read by nothing — no error, no failure, no log line, `authDebug` or not (the user's rule: every redaction attempt had a bypass, so there is no redactor and no regex over server text; `equivalentEncodings.test.ts` proves with a decoding oracle, on a real socket through every site and both paths, that no surface holds a secret or the server's text). **Secrets reach a log line only through `prepareSecret(value, authDebug)`** (`tokenRequest.ts`), called at the point of logging with the secret as a separate value, never applied to a finished line: without `authDebug`, `<redacted, N chars>`; with it, the first 4 and last 4 characters around the marker, the length only below 16 characters. **The failure line** (`failedRequest`, `sendTokenRequest`): by default 5.4.2's safe-facts `debug` line `<operation phrase>: the token endpoint refused the request`, `{ status, error?, code? }` — none for the device poll's `authorization_pending` / `slow_down` with status `400`, none without a logger; only with the provider's `authDebug: true` instead `[<operation>] token endpoint said`, `{ status, error?, code?, sent }`, where `sent` names every secret the request carried — the site's (`grantSecrets`, the configured `client_secret`), its legacy Basic credential (`legacyBasic` → `basic`, `basic_secret`) and the strategy's (`client_secret`, `client_assertion`, a Basic credential) — joined by one function (`sentOf`) for both this line and `rejectMissingToken`'s (a `200` without a token: 5.4.2's `error`-level line verbatim at the UAA code exchange, a `debug` line elsewhere). `authDebug` is read once by `BaseTokenProvider` as `config.authDebug === true`, never from the environment, and handed to every site in its `TokenRequestSite`. Every log call on a failure path goes through `logQuietly`: a logger that throws, or answers a rejecting promise (adopted like any thenable, with a contained handler), cannot replace the failure the site throws. **No error's message reaches a log line either:** a line about a thrown value logs `logFields(classify(error, operation))` — `{ error: reason, kind, status?, diagnostics? }` — never `message`, `cause`, `stack`, `String(error)` or a serialised error. A consumer's strategy, loader, presenter, validator, renewal or persistence strategy, store write, launcher or SNC locator/probe may throw text holding a secret (`noTokensInLogs.test.ts`, `thrownMessages.test.ts`). **What a token site throws:** `sendTokenRequest` turns any rejection — an axios failure, or what a consumer's global interceptor threw (the server's text, a primitive, a Proxy, an object with throwing getters) — into an `AuthProviderFailure` built right there: `tls` for an allowlisted TLS code, else `request-failed` with the operation, the grant, `problem` (`refused` with an integer status, `no-response` without), a registered `oauthError` and an allowlisted system `code`; an abort of the attempt's own signal is `interactive-login` `aborted`; no `cause`, no request, no foreign value (`foreignRejections.test.ts`, `canceledRequests.test.ts`). OIDC discovery classifies its failures the same way (`requestFailure`). A successful answer is never handed to a site either: `sendTokenRequest` returns a snapshot — an integer status and a plain `data` of the expected fields, each read through `readSafely` and kept only with its protocol type (`answerData`: a token or device field a non-empty string, `expires_in` / `interval` a finite non-negative JSON number; anything else absent, so `{"access_token":42}` is `no-access-token`) — and an answer that cannot be read is `request-failed` `incomplete-response`; OIDC discovery keeps a snapshot of the fields the providers read (`DISCOVERY_FIELDS`, the two mTLS aliases), and an aborted or failed discovery is not cached. Every property of a foreign value is read through `readSafely` (`src/auth/knownCodes.ts`): a throwing getter or Proxy reads as absent. **Every end of an interactive login** is an `AuthProviderFailure` of `interactive-login` (`src/auth/interactiveLogin.ts`, one outcome per way a login ends) — port in use ("already in use", kept for any consumer that may match it), aborted (`strategy: 'browser' | 'manual'`, the ignored-callback tally), disposed, busy, the IdP's `?error=` on the callback naming only a registered code (`error_description` and `error_uri` reach only the escaped error page), a presenter that threw (`device-code-not-shown`), and `failed` for anything else (an integer status, a registered `error`, an allowlisted code; no `cause`). A configuration mismatch found while building the URL is a `configuration` failure, relayed as it is. A launcher's failure is not an end: it is logged in fixed words, the URL is prompted, and the login keeps waiting.

**No URL and no configured or server-supplied string in a log line.** A line carries fixed words and admitted facts only (operation, grant, status, registered code, `logFields` of a failure, a token's `<redacted, N chars>`): never a discovery URL, an endpoint, a UAA URL, a redirect URI, a client id — a discovered value is the server's text, a configured one may hold a credential. `logCallSources.test.ts` scans every log call, prompt and `stderr.write` in `src` for identifiers naming a URL, endpoint, client id, issuer, scope, message, … (plain code over our own source); `endpointsInLogs.test.ts` proves it on a real socket with hostile discovery documents and configured endpoints, `authDebug` absent, `false`, `true`. **Prompts** (`announce`, the one place a URL is shown — the authorization URL, the verification URI) show a URL only through `promptableUrl` (`src/auth/announce.ts`: an http(s) serialisation of printable ASCII, else fixed words) and the device user code only through `promptableText`; a prompt variable carrying a URL is named `shown…`, and an announcer is bound to a name before use, so the scan sees every prompt. The approved exception: `SncLogonProvider`'s `debug` line names the resolved library path as an admitted `LocalPath`.

**Options are read as own data.** Every exported constructor and factory reads its options object through `ownOptions` (`src/auth/configuration.ts`): a plain snapshot of own data properties, an accessor never run, a throwing Proxy read as absent, a non-object empty — so it throws only its own `configuration` failure (`hostileOptions.test.ts`: throwing Proxies, getters, revoked Proxies, primitives; hostile collaborators). A collaborator is read only guarded (`readSafely`, `isShippedValidator`'s descriptor read) and called inside a moment. A strategy or loader called directly by the consumer, outside a moment, may still reject with its own collaborator's throw (README, "Errors outside the moments").

**Nothing writes to `process.stdout`.** Under an MCP or LSP stdio transport, stdout carries protocol traffic, and a stray line corrupts it. Prompts go to the `ILogger` when there is one and to `process.stderr` when there is not — see `src/auth/announce.ts`. A prompt that vanishes without a logger is also a bug: a user who cannot see a device code cannot finish the flow.

### Package responsibilities

This package ONLY:
- implements `IAuthProvider` — every credential a process delegates to — and, for the token providers, `IRefreshableTokenProvider` beside it
- builds authorization URLs and exchanges codes, assertions and refresh tokens for tokens
- ships strategies, validators and named static factories for conducting an interactive authorization or assembling a common recipe
- validates SAML assertions, with two shipped validators and an in-memory replay store, all replaceable
- resolves the SNC library for a passwordless RFC logon (`SncLogonProvider`), producing logon parameters only

This package does NOT:
- store tokens (`@mcp-abap-adt/auth-stores`)
- orchestrate authentication (`@mcp-abap-adt/auth-broker`)
- load service keys or manage sessions
- decide how a user reaches an authorization URL, or where the redirect is received — the consumer may replace both
- fetch identity provider metadata — certificates and entity IDs come from configuration
- open a connection or speak RFC/HTTP itself — `SncLogonProvider` depends on neither `@mcp-abap-adt/sap-rfc-lite` nor `@mcp-abap-adt/connection`

### How an interactive login works

A provider owns what it can compute: the authorization URL and the token exchange. Everything between them belongs to an `IAuthorizationStrategy`:

1. the provider hands the strategy an `AuthorizationRequest` carrying `buildAuthorizationUrl(redirectUri)`;
2. the strategy decides where the redirect will be received, then asks for the URL — that ordering is what makes an ephemeral port possible, since the URL cannot be assembled before the socket is bound;
3. the strategy returns an `AuthorizationOutcome` carrying the payload **and** the redirect URI that actually took part, because the token exchange must send the same one.

Ship-default strategies: `browserCallbackStrategy`, `oidcCallbackStrategy`, `samlCallbackStrategy`, `manualPasteStrategy`, `manualSamlResponseStrategy`, `externalCodeStrategy`, `staticCodeStrategy`.

**Lifecycle: whoever constructs, disposes.** A provider builds no strategy of its own (rule 7) and disposes none: the strategy it is given — by the consumer, or composed by a static factory (`inBrowser`, `fromTerminal`) the consumer called — lives as long as the provider and is used for every login; the consumer owns it and disposes it when done, since the point of a long-lived receiver is to outlive one login. `dispose()` disables a strategy permanently and ends its logins in flight (`disposed`); an abort through `signal` ends only the login (`aborted`) and leaves the strategy usable.

### Cancellable shared attempts

`BaseTokenProvider`'s renewal and pin run through auth-errors' `sharedAttempt` (never a local waiter implementation): `getTokens({ signal })` / `refreshTokens({ signal })` join as waiters; a moment joins with the attached parties (`config.signal`, `attach(signal)`, auth-errors' `createParties`), its `MomentWaiter` released in a `finally`; with no live party a moment's login is unbounded. Every effect goes through one serialized commit queue (`commit`) with two watermarks — pin and credential generations, taken when the attempt begins; a login's result commits only if its attempt was not aborted, a refresh's result whenever nothing newer was committed. `performLogin(attempt)` hands `attempt.signal` to the strategy (`AuthorizationRequest.signal`, interfaces-auth 6.0.0, read through `signalOf`) and to every request (`siteOptions(attempt.signal)` → `attemptSite`), and runs the strategy's `authorize` (or the whole device flow) inside `attempt.exclusive` — the drain. `performRefresh(refreshToken, signal, dispatched)` sends the token the base read and calls `dispatched()` right before the request leaves (`sendTokenRequest`, both paths); refresh sites never read a signal, so a dispatched refresh runs on. The abort handler acts only after `dispatched()`: it records the observation and applies the decision's `ifCut` — `discard` adds the token to `discarded` (lifetime) and queues its clearing and `refresh-token-discarded` report, `keep` does nothing; an abort before dispatch touches no refresh token. One credential generation per step. Every report to `persistence` is made from the commit queue in commit order — awaited while the attempt has a live waiter (its failure is the renewal's, `unknown` `persisting-tokens`, the credentials kept), detached otherwise (logged once in fixed words, never attributed to a later call); none for a cache hit, a watermark-discarded commit or a discard of a token no longer held; never twice. The logical refresh state and pending delivery live only in `refreshStatePersistence`. Concurrency tests: `sharedAttempts`, `commitQueue`, `refreshAfterDispatch` (real socket), `drainHandoff`, `attemptSignals`, `renewalStrategy`, `renewalOnTheWire`, `persistenceReports`, `persistence/refreshStatePersistence`, and `raceScenarios` under plain node (`helpers/plainNode.ts`, an unhandled-rejection recorder).

### Client authentication

`IClientAuthentication.authenticate(draft)` — the draft carries the endpoint, the server's mTLS alias (`mtlsAlias`, from discovery of an endpoint not given in configuration), the client id and the grant type, never a secret or a previous response — returns `{ endpoint?, parameters?, headers? }`; `tlsMaterial?()` the certificate it presents.

- **One path with a strategy, today's request without one.** Every site that sends to an authorization server (client credentials, UAA refresh, code exchange, passcode, SAML exchange and refresh, every OIDC request, device initiation included) takes an optional `TokenRequestAuth`. With it, `prepareTokenRequest` (`src/auth/tokenRequest.ts`) builds the grant's own parameters plus the strategy's, checks the result before anything is sent — strings only, no line break in a header, nothing replacing the site's own parameters or headers, an absolute `https:` endpoint (`http:` only when the configured one is `http:` and there is no material), else `client-authentication` `result-unsendable` — sends through an `https.Agent` built from exactly the four material fields (`rejectUnauthorized` never set; a private CA is `NODE_EXTRA_CA_CERTS`; no `ca` option), with `maxRedirects: 0`. Without it, each site's private adapter sends exactly the pre-strategy request, also with `maxRedirects: 0`; `tokenRequestShapes.test.ts` pins every site's shape, and `tokenRequestRedirect.test.ts` proves on real sockets that no site, on either path, follows a 307. OIDC discovery is the one request that follows redirects: a GET for public metadata, no secret.
- **Errors carry no request, and nothing of the server but facts, on both paths.** A failed request throws the `AuthProviderFailure` `sendTokenRequest` built (see "No token … reaches a log line"): no `config`, `request`, form body, `Authorization` header or TLS agent with key/PFX/passphrase is reachable from it, and it has no `cause`; `tokenRequestRedirect.test.ts` proves on a real socket that a reason phrase holding a secret survives in no rendering of the failure, on either path. Every site builds its legacy Basic header only through `legacyBasic(clientId, clientSecret)` (`tokenRequest.ts`), whose `secrets` come from the same `basicSecrets()` as a strategy's, so `sent` names it under `authDebug`; outside `legacyBasic` and `clientSecretBasic` no file in `src` writes a `Basic ` header or base64-encodes a value (`BasicAuthProvider`, the AuthnRequest and PKCE excepted; `basicHeaderSources.test.ts`, and the shape check's rule 8), and `basicCredentialEcho.test.ts` proves on a real socket that a server echoing the header, in a `400` or a `200` without a token, gets nothing of it, nor any of its own text, back out. A secret a custom strategy puts in another parameter or header is not named in `sent` — and is logged nowhere either way. A TLS failure on the allowlist (`TLS_FAILURE_CODES`) is kind `tls`, in words fixed per kind of failure (auth-errors renders them): untrusted server certificate → hint `NODE_EXTRA_CA_CERTS`; `CERT_HAS_EXPIRED` and `ERR_TLS_CERT_ALTNAME_INVALID` their own; a server's alert refusing the client certificate (both OpenSSL spellings, `SSL/TLS_ALERT_…` and `SSLV3_ALERT_…`) → "the server refused the client certificate". No token request and no OIDC discovery carries a timeout of the package's choosing: the attempt's signal is the bound (a refresh's request is never given one: see "Cancellable shared attempts").
- **`clientSecret` beside a strategy is a configuration error** (`client-secret-beside-client-authentication`) naming `clientSecret`, decided in the `BaseTokenProvider` constructor on presence (`!== undefined`), so `''` counts. Where `clientSecret` was required (`ClientCredentialsProvider`, `AuthorizationCodeProvider`), a strategy satisfies it.
- **Pinning** (`BaseTokenProvider.pin`): once per lifetime, concurrent first needs share one attempt, a failed read pins nothing and the next moment reads again; `renewOnce()` pins (through `presentable()`) before the strategy is asked or anything is sent, so unusable material refuses the renewal whole. The material is copied (Buffers too) so a strategy changing its object later changes nothing.
- **What a strategy or loader throws** goes through `classify`: this package's own failures (`client-certificate`, `client-authentication`, `configuration`) are answered as they are; any other error (a loader's `ENOENT`) is `unknown` with the operation and the grant — "`<auth type>` token request failed (unknown error, CODE)" — by design (rule 2).
- **The opaque-token limit.** A provider learns a binding only from the token; it does not introspect. An opaque token bound to a certificate needs the certificate strategy configured, or it goes as a plain Bearer and is refused `401` by the resource.

### SAML assertion validation

A SAML provider validates the payload before anything else uses it — `Saml2BearerProvider` before the token exchange, `Saml2PureProvider` before `cookieProvider`, whose `expiresAt` comes from the result. The validator is given to the constructor (rule 7): without `assertionValidator` the constructor throws a configuration error (`required-fields-missing`, naming `assertionValidator`) — and so does a missing `idpEntityId` beside a shipped validator supplied as `assertionValidator` (`saml-shipped-validator-without-issuer`), recognised by a module-private, non-enumerable symbol both factories set. A custom validator needs no `idpEntityId`.

- **Two validators, chosen by identifier, not by option.** `createSignedResponseValidator` requires the `Response` signed and runs all twelve checks — `Saml2PureProvider`'s default. `createSignedAssertionValidator` requires the `Assertion` signed, accepts a bare one, and does not read `Status`, `Response/Issuer` or `Destination` — `Saml2BearerProvider`'s default, since the token endpoint gets the Assertion alone.
- **Everything is read from the signed element.** Every signature must verify and envelope its target; every SAML 2.0 `Assertion`/`EncryptedAssertion` and every SAML 1.x `Assertion` must be the signed one or inside it — and never inside a `ds:Signature`, whose subtree an enveloped signature leaves unsigned; IDs must be unique. The assertion-only validator reads the bare root `Assertion` or the Response's direct-child one, never merely the first covered. Every required field is refused when absent; of the fields the validators read, only `NotBefore` (Conditions and bearer confirmation), `Response/Issuer` and `NameID` may be missing (`nameId` is `undefined` when the `Subject` carries none or more than one). A `<!DOCTYPE` is refused before parsing; XML is parsed with `parseStrictXml` (`src/auth/strictXml.ts`), which throws on every parser fault and never writes to the console; `KeyInfo` certificates are never used; SHA-1 is accepted (xml-crypto defaults).
- **The request ID is minted, declared (`authnRequestId`) or declared absent (`idpInitiated: true`)** — never inferred. Neither is a configuration error raised after the strategy returns; `idpInitiated` with a declared ID is one raised at construction (`validateSamlConfig`); `idpInitiated` without `authorizationUrl` makes `buildAuthorizationUrl` throw before any URL exists. UAA and XSUAA refuse `InResponseTo` on the saml2-bearer grant, so bearer against them needs `idpInitiated`.
- **Shipped validators fail closed without `expectedIssuer`.** Providers always pass `idpEntityId`.
- **Every refusal names its rule.** Each SAML refusal is an `AuthProviderFailure` of a minted `saml-assertion` error (56 rules — the validators' 50 and the bearer conversion's 6, listed in the README's "Refusal messages"), built at its site with `authError['saml-assertion']({ rule, check, … }, { … })` and thrown by `refuse` (`src/validation/samlRefusal.ts`, whose parameter names no rule so the rule — and with it the check and the one permitted diagnostic — is inferred from the literal and checked by the compiler; `samlDiagnostics.typecheck.ts`). No two rules under one `check` share words, and every test asserts the rule, the check, the fragment only its rule produces and the diagnostic or its absence (`helpers/samlRefusal.ts`; `samlRules.test.ts` checks the fragments are unique and every rule is asserted at its site). An element that must appear exactly once distinguishes absent from more than one (`requireOne`, a rule each, the count a fact). `no-bearer-qualifies` is existential and lists each candidate's first failed sub-rule in a fixed order (`readConfirmation`) as `BearerCandidate` facts, five listed and the rest counted in `moreCandidates`. **No document value is in the words:** a value a rule may show (root name, duplicated ID, reference URI, unregistered StatusCode — a registered one is the `statusCode` fact —, Issuer, invalid Conditions time, Destination) is passed as that rule's one diagnostic and admitted by its shape or dropped by auth-errors; nothing a parser, xml-crypto or OpenSSL says reaches the error — `parseStrictXml` refuses `not-xml` itself, dropping xmldom's `ParseError`. **No regular expression runs over the document** (the DOCTYPE probe, `xsd:dateTime`, the certificate armour are plain code; `samlSources.test.ts`). A custom validator's throw is classified with `validating-assertion` (`validateAssertion`); a shipped validator's refusal it passes on stays as it is. The signed-Response validator reads `Status` (inside the signed Response) right after the signature checks and before counting the `Assertion`, so a declined login — which carries none — is refused `declined` with its status (the assertion-only validator never reads `Status`). The Response's direct-child `Assertion` is counted before placement; once placement pins the signed element to the one required, no further identity check can fire, so there is none — the wrapping attacks are refused by count or placement, each with a test through `validate()`. Nothing is exported for tests. The README's "Refusal messages" tables (every rule, and the eleven bearer candidate reasons) are generated from auth-errors' words (`npm run docs:tables`, `scripts/generate-refusal-tables.mjs`).
- **Replay store is process-wide** (`defaultReplayStore`), keyed `{issuer, assertionId}`, retained to min(`Conditions/@NotOnOrAfter`, the latest bearer `NotOnOrAfter` that answers the request and names the ACS, one not yet open included) + `clockSkewMs` — not `expiresAt`, which takes the earliest. `clockSkewMs` defaults to 0.

### Callback server

`runCallbackScope` owns the socket for the duration of one scope. It is released on the first terminal outcome — the body returning or throwing, an explicit failure, the IdP's refusal, or an abort — and the factory settles only once the listening socket is closed, so a settled promise always means the port is free. **No timer of the package's choosing** (the user's rule): no login timeout, no shutdown grace — at release an idle connection is ended and unreferenced, one whose request body is unfinished is destroyed, and one whose complete request is still being answered is unreferenced while its response goes on (`callbackAbortBody.test.ts`). Measured limits: `http.Server.close()` destroys a parsed connection even mid-flush of a large response to a client that does not read, and a pending write keeps the loop alive whatever `unref()` says. `ICallbackServerOptions` (interfaces-auth 6.0.0) has no `timeoutMs`; `signal` is the only way a scope ends without a result, and no `timeoutMs` is left in `src` (`interactiveSources.test.ts`). Each shipped strategy settles its `authorize` only after its release — the browser strategies after the factory settles, the manual ones after their reader (the `readline` closed, its stdin listeners gone) — which the next login's drain waits for (see "Cancellable shared attempts").

- `port: 0` binds an ephemeral port; `handle.port` and `handle.redirectUri` report what the OS gave. Not usable where the redirect is registered with the identity provider, as a SAML ACS always is.
- The default port is **61001** — above Linux's `ip_local_port_range` (32768–60999) and clear of the 3001/3333 range application servers use. There is no default login timeout: a login ends on its result, the IdP's refusal or the consumer's `AbortSignal` (compose `AbortSignal.timeout(ms)` for a bound; the factories take `{ signal }`).
- **Every page is safe to render.** A value interpolated into a page goes through `escapeHtml` (the IdP's `error` / `error_description` are attacker-controllable query parameters); pages go out through `sendHtml` (`text/html; charset=utf-8`), short answers through `sendText` (`text/plain`); a middleware sets `X-Content-Type-Options: nosniff` and a CSP of `default-src 'none'` (inline style and a same-origin form only) on every response (`callbackPages.test.ts`).
- **Login CSRF.** The shipped transports bind `127.0.0.1`, then `::1` on the same port (or only the consumer's `host`); `EADDRINUSE` on `::1` fails `port-in-use`, `port: 0` included, while a host without IPv6 loopback (`EADDRNOTAVAIL` / `EAFNOSUPPORT`) listens on `127.0.0.1` alone. A `Host` check runs before every route: `Host` and `allowedHosts` read through the WHATWG URL host parser, a loopback authority only from a loopback peer with the bound port, `0.0.0.0` / `[::]` never. `browserCallbackStrategy` / `oidcCallbackStrategy` open `gated` and arm with the authorization URL's `state` (`expectState`) before the browser opens; a transport without `expectState` is `configuration` `invalid-value ['callbackServer']`; the UAA paste form carries a per-arming form token; a pasted input is a bare code only without `? & = / #`. Providers mint `state` (and, for UAA too, PKCE) only for a URL they build.
- Every request the transport refuses — no payload, a wrong or missing `state`, before arming, no form token, a foreign `Host` — is answered `400`, counted and **ignored**; the login keeps waiting, and its `aborted` words report "N request(s) to the callback server were refused and ignored" (`ignoredCallbacks`, auth-errors 2.0.1). An explicit `error=` with the right `state` still ends the login at once.

## Testing

**Unit tests** mock axios or the module boundary. **Integration tests** need `tests/test-config.yaml` (copy `tests/test-config.yaml.template`) and skip without it. **A default run opens no browser:** the browser-login cases in `AuthorizationCodeProvider.test.ts` and `browserAuth.integration.test.ts` run only with `interactive_login: true` in the config or `MCP_ABAP_ADT_INTERACTIVE=1`. Two conventions worth knowing, each of which has cost a debugging round:

- **Attach a rejection expectation before triggering it.** `const rejected = expect(p).rejects.toThrow(…)` first, then deliver the request, then `await rejected`. Awaiting the trigger first leaves the promise unhandled at the moment it rejects, and Jest reports an unhandled rejection instead of a passing assertion.
- **Assert on the port, not on a log line.** Anything claiming a socket was released binds it to prove it. Log output proves nothing — code paths have claimed a port was freed without calling `close()`.

When a test is meant to protect a rule, prove it is load-bearing: break the rule deliberately, watch the test go red, revert. Tests have passed here while the rule they existed to protect could be deleted outright.

## Error classes

There are none in this package. Every throw is auth-errors' `AuthProviderFailure` holding a minted `IAuthProviderError` of its kind, and every refusal is such an error; `getTokens()` / `refreshTokens()` throw nothing else — a collaborator's own throw is classified, never rethrown as itself, and no `AxiosError` escapes. The kinds this package produces: `configuration`, `client-certificate`, `client-authentication`, `request-failed`, `tls`, `interactive-login`, `saml-assertion`, `snc`, `credential-refused`, `system-refused`, `renewal-unchanged`, `token-binding`, `not-prepared`, `logon-target` (a target's answer relayed), `renewal-declined` and `unknown` (with, among its operations, `renewal-strategy` and `persisting-tokens`). A consumer reads one with `readFailure(thrown, operation)` and switches on `kind` exhaustively (`matchKind`, or `unreachableKind` in a `default`); never `instanceof`. The 5.x classes (`TokenProviderError`, `ValidationError`, `RefreshError`, `SessionDataError`, `ServiceKeyError`, `BrowserAuthError`, `AssertionValidationError`, `CertificateMaterialError`, `ClientAuthenticationError`, `ClientAuthenticationResultError`, `BasicClientIdError`, `TokenEndpointError`, and the internal `CallbackScopeError`, `AuthorizationRefusedError`, `DeviceCodePresentationError`, `SncLibraryNotFoundError`) were deleted in 6.0.0; `throwSweep.test.ts` refuses any `new Error(`, any construction of a deleted class and any refusal from free words in `src`, and `transitionCoverage.test.ts` checks no transition piece of the migration is left. The README's refusal tables are generated from auth-errors' words (`npm run docs:tables`, `scripts/generate-refusal-tables.mjs`); `readmeRefusalTables.test.ts` fails when the committed README differs — the "When" / "The rejection" cells are hand-written context in the script, the word cells rendered.
